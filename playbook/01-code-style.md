# 01 代码级规范

> 归属：AI Coding Agent 软件工程手册

这一章决定代码的日常质量。架构正确但函数写成 200 行、命名靠猜，系统一样会烂。

## 命名

- **名字回答三件事**：为什么存在、做什么、怎么用。`days_since_creation` 优于 `d`，`inactive_users` 优于 `list2`。
- **一个概念一个词。** 取数不要在 `fetch` / `get` / `retrieve` 之间摇摆。同名不同义、同义不同名，都是后续误解的来源。
- **禁止编码噪音**：类型前缀（`str_name`）、成员前缀（`m_`）、无意义缩写（`usr`、`cfg`；`i`、`idx` 只允许用于循环变量）。
- **可搜索**。单字母名只允许出现在循环体和极短闭包中。数字常量必须有名字。
- **可发音**。读不出来的名字在评审时没人愿意提。
- **布尔用前缀**：`is_`、`has_`、`can_`、`should_`，且不用否定式（`is_empty` 而非 `not_ready`）。
- **长度与作用域成正比**：循环变量 1-2 字符，局部变量短，公开 API 全拼。

## 函数

- **只做一件事。** 判断标准：能否用一句话描述，且这句话里没有"并且"。
- **函数体内每行处在同一抽象层。** 高层函数调用下层函数，不要在中间插入一行 SQL。
- **参数不超过 3 个**（硬上限 4）。超过时用具名对象、配置结构体或构造器传递。
- **禁止标志参数**。`save(user, notify=True)` 说明这是两个函数。
- **禁止输出参数**。用返回值给结果，不要通过修改入参返回。
- **命令与查询分离**：要么改变状态，要么返回信息。
- **提前返回优先**。守卫子句把嵌套拍平到 3 层内。**不限制 return 条数**——为了减少 return 而加深嵌套是净损失。
- **长度**：新代码 ≤ 40 行，硬上限 80 行。
- **读操作不带副作用**。`get_user()` 不该顺手更新最后登录时间。

## 注释

- **代码说"怎么做"，注释说"为什么"。** 复述代码的注释是负资产，因为它会过时并误导。
- **必须写的**：非显然的业务约束、绕过某个 bug 的原因、性能取舍、外部接口的诡异行为、安全相关的不变量。
- **禁止写的**：改动历史（git 记得）、被注释掉的代码（删掉）、位置分隔符、作者署名。
- **TODO 必须带条件**：`TODO(issue-123): 临时绕过，等上游修复`。没有归属的 TODO 等于永久债务。
- **公开 API 必须有文档注释**：做什么、参数含义、可能的错误、什么情况下会 panic 或抛异常。
- 注释语言跟随项目；错误消息和日志键名用英文。

## 格式

- **格式交给工具**，禁止手工对齐。提交前必须过格式化检查。
- **文件像报纸**：顶部是标题和高层概念，细节依次向下。读前三行就该知道这是什么。
- **就近原则**：变量声明靠近首次使用；私有辅助函数靠近调用点；公开入口在上，内部实现在下。
- **导入分组固定**：标准库、第三方、本项目；禁止通配符导入。

## 对象与数据结构

- **对象藏数据、露行为；数据结构露数据、无行为。** 不要混用。给 DTO 加业务方法，或给领域对象加公开字段，都会破坏这个对称性。
- **迪米特法则**：只和直接朋友说话。`order.customer.address.city` 是三次越界，让 `order` 提供 `shipping_city()`。
- **DTO 只做跨边界的数据搬运**，不承载业务规则；领域对象不实现序列化细节。

## 错误处理

- **错误是值，不是异常流。** 用返回类型表达可预期的失败（Rust `Result`、Go `error`、TS discriminated union、Python 具名异常），不用裸字符串或布尔值。
- **在边界转换错误**：外部库的错误在适配器层转成领域错误；领域层不感知 HTTP 状态码或数据库错误码。
- **不吞错误**。每一层要么处理，要么附加上下文后上抛。空 catch 块是最严重的一类 bug。
- **不用 `null` / `None` 表示失败**。用 Option、Result 或专门错误类型；确实需要"空对象"时用 Null Object 模式。
- **失败要早**：参数非法、前置条件不满足，在校验点立即失败，不要带坏数据往下跑。
- **区分可重试与不可重试**，在类型或字段上体现，重试逻辑不允许靠猜。
- **不用异常做控制流**。用异常跳出多层循环、用异常表示"没找到"，都会让调用方无法区分正常与异常。

## 重复

- **三次法则**：第一次直接写，第二次复制，第三次抽象。第二次就抽象往往抽错。
- **消除"同时变化"的重复，不消除长得像的重复**。两个函数现在一样，但变化原因不同，就不该合并。
- **抽象的前提是能命名**。抽出来的东西想不出准确名字，说明还没理解它是什么。

## 复杂度预算

统一阈值，全项目一份，不要每个模块各定一套。

| 指标 | 阈值 | 超限动作 |
| --- | --- | --- |
| 单文件行数 | 400 | 按职责拆分 |
| 单函数行数 | 80（目标 40） | 抽子函数 |
| 嵌套深度 | 3 | 守卫子句 / 提取 |
| 函数参数 | 4 | 引入参数对象 |
| 圈复杂度 | 10 | 拆分支 / 用多态替代条件 |
| 单类或结构体公开方法 | 20 | 检查是否承担多个职责 |
| 单模块对外依赖 | 10 | 检查边界是否划错 |

阈值是默认值。项目有实测依据可以调整，但要在 README 或 ADR 写明依据，不能静默放宽。

## 代码味道清单

评审时按此扫描，命中即需说明或修改：

过长函数、过大类、过长参数列表、重复代码、深层嵌套、魔法数字、布尔标志参数、`switch` / `if` 类型分发（一个类型判断只应出现在一处，且产出多态对象）、依恋情结（方法大量访问别的对象的数据，应搬家）、数据泥团（三四个参数总是结伴出现，应成为对象）、基本类型偏执（用裸 `str` / `int` 表达有语义的概念）、发散式变化（一个类因多个不相关原因被修改）、霰弹式修改（一个改动要动八个文件）、中间人（只做转发的类）、过长的消息链、夸夸其谈的通用性（为不存在的需求写框架）。
