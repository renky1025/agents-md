# 04 工程流程

> 归属：AI Coding Agent 软件工程手册

## 版本控制

- **小步提交**，一次提交一件事。混着重构和功能变更的提交无法回滚。
- **提交信息说明 why**，不只写 what。`fix: 预热连接池，避免冷启动 5s 超时` 优于 `fix bug`。
- **禁止直接提交 main**。分支 + PR，即使是单人项目。
- **禁止提交生成物、密钥、本地配置**。提交前检查 `git diff`。

## 代码评审

- **PR 控制在 400 行改动以内**。超过就拆；评审质量随规模断崖下降。
- **评审看设计**：边界是否清楚、命名是否准确、错误处理是否完整、测试是否覆盖失败路径、是否引入新依赖。
- **格式问题交给工具**，评审不讨论缩进和引号。
- **每条意见必须可执行**：指出问题、给出方向，不只说"这里不好"。

## 架构决策记录（ADR）

- **仅在决策难以逆转时写**：数据结构、对外 API 契约、技术选型、跨模块边界。日常改动不写 ADR。
- 内容：背景、可选方案、选择、后果（代价与放弃的东西）。
- 写在 `docs/adr/`，编号递增；不修改历史 ADR，只追加新条目推翻旧的。

## 技术债

- **新增代码前评估**：是否增加耦合、是否破坏已有边界、是否引入新的运行时依赖、三个月后改这块要多久。
- **债务显式化**：发现的债务记录在 issue 或 TODO，带成因与修复成本。静默累积的债务最终以"整个模块重写"的形式一次性偿还。
- **还债优先级**：挡住当前需求的债先还；不挡路的债排队，不顺手改。

## CI 门禁

提交必须自动通过：格式化检查、lint、类型检查、单元测试、依赖漏洞审计。

**禁止"先合再修"**。红灯分支不允许合并，也不允许用 `--no-verify` 绕过钩子。

## 发布

- **环境顺序**：staging -> 灰度 -> 生产。禁止跳过灰度直接全量。
- **破坏性变更**：API 走版本化或双写过渡；数据库变更必须向前兼容（先加列、再双写、再切读、最后删旧列），每一步可回滚。
- **功能用开关控制**，让代码合入与功能上线解耦。
